# Agent 与工作流：把重复任务交出去

过去三个月我把几件每周都要干的事交给了脚本和 Agent。结论先说：**能用确定性工作流解决的，别用 Agent；需要开放判断的，才让 Agent 上。** 这两类任务我差不多各占一半。

## 我的任务清单

| 任务 | 频率 | 原来耗时 | 现在方式 | 现在耗时 |
|---|---|---|---|---|
| 周报素材整理 | 每周 | 40 分钟 | 固定工作流 | 6 分钟 |
| 资料归档打标 | 每周 | 30 分钟 | Agent + 规则兜底 | 8 分钟 |
| 竞品动态早报 | 每天 | 25 分钟 | 固定工作流 | 2 分钟 |
| 会议纪要提炼 | 每周 | 20 分钟 | Agent 起草 + 人改 | 12 分钟 |

落地页监控这种固定链路，用 DAG 工作流：抓取、清洗、去重、摘要、写回表格。每一步都能单独重跑，出错看日志就知道卡在哪。

资料归档则不确定：标题格式乱、标签要理解内容。先让 Agent 读全文给 3 个候选标签，再走一道规则兜底（标签必须在已有词表里），两头各管一段。

## 我踩过的四个坑

1. **没有停止条件**：第一版 Agent 会把同一个链接反复抓七次，因为工具返回空它也当没完成。加了 max_steps=8 和单任务 120 秒超时后才稳定。
2. **工具返回太长**：把 5000 字的网页直接塞回上下文，模型后半段开始胡说。现在工具结果统一截到 1500 字，并注明被截断。
3. **日志缺失**：出问题时只有一句「任务失败」，根本不知道哪一步。现在每步记 `task_id / step / 输入摘要 / 耗时 / 结果`，复盘全靠它。
4. **让 Agent 直接改文件**：有一次误删了归档目录里的两个文件，从此写操作一律先写临时目录，人确认后再落盘。

## 什么时候不值得自动化

判断标准我写进了《我的决策清单》：一件事如果每月总耗时不到 15 分钟，或者一年只做两次，就不自动化，维护成本比收益高。这条拦下了好几个「看起来酷」的项目。

## 工作流、Agent、提示词的分工

工作流负责确定性，Agent 负责判断，提示词决定判断的质量。我给每个步骤写 prompt 的格式在《提示词工程踩坑笔记》里：角色、输入、输出格式、失败时怎么办四段。

另外每次运行结束写一条两行复盘，周日一起看。上个月发现「资料归档」失败的原因 80% 是标题里带日期格式，规则补一条就解决了。自动化的收益不在第一次省下多少时间，在于它每天逼你把流程想清楚一次。

## 我怎么记录运行

每次运行写一行 JSON：任务名、开始时间、步骤数、状态、失败原因、耗时。一周汇总一次，看失败率最高的任务，通常是输入格式变了。日志不用漂亮，但必须能用来复盘，这个习惯是从《我的决策清单》的决策日志搬过来的。
