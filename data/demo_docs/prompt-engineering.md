# 提示词工程踩坑笔记

我平时用提示词的场景就三类：信息抽取、改写润色、多步任务编排。前两类用同一条经验就能覆盖：**把要求写成可检查的条件，而不是形容词。**

## 我的四段式模板

1. **角色与目标**：一句话说清「你是谁、这次要产出什么」。
2. **输入**：原文、可用的背景、以及不该看的东西。
3. **约束**：字数、格式、必须包含和必须避免的内容。
4. **输出与兜底**：JSON schema 或 Markdown 结构，以及信息不足时输出什么。

## 改前改后对比

| 写法 | 抽取字段完整率 |
|---|---|
| 「请仔细、务必、认真地提取」 | 71% |
| 「提取 title、date、amount 三个字段；缺失填 null；只输出 JSON」 | 94% |

「务必」「认真」这类词对模型基本无效，反而让它输出更多解释性废话。真正有用的是把验收标准写出来：字段名、是否允许 null、要不要解释。

## 五条具体做法

- **示例胜过描述**：给 2–3 个 few-shot，比写一段规则更稳，尤其是格式类任务。
- **温度按任务定**：抽取和结构化输出用 0.1–0.2，创意类 0.7；我基本不碰 0.9 以上，中文长文会开始跑偏。
- **输出必须校验**：JSON 解析失败就带着报错让模型重修一次，成功率从 88% 到 99%。这段重试逻辑比 prompt 本身重要。
- **少用「让我一步步思考」**：在本地 7B 模型上，它会把答案淹没在大段推导里；换成「先列要点再给结论，总字数不超过 200」更直接。
- **上下文要分段标注**：资料之间用编号和标题隔开，别糊成一坨。这跟《RAG 检索增强生成实践笔记》里给资料加编号是同一个理由。

## 一个真实失败

让模型把会议转写整理成待办清单，输出格式写的是「- 负责人：事项」。结果它把「负责人」猜成了纪要里的发言人。后来改成：先抽说话人和句子，再匹配「我来」「我负责」这类原文线索，无法判断的标「待确认」。**宁可留空，也不要让它猜。** 这条后来也写进了《技术写作与金字塔原理》的写作规范：不确定的地方明确标注，不糊弄。

## 怎么评估

我维护一个 20 条的 mini 测试集，覆盖抽取、改写、拒答三类需求。每次改 prompt 就跑一遍，看通过率。没有测试集的时候改 prompt 全靠感觉，改了十版也不知道哪版好。

## 和 Agent 的关系

单步 prompt 是砖，Agent 是把砖砌成流程。砖不合格，流程再花哨也没用，所以《Agent 与工作流》里我把评估放在最前面做。

## 系统提示词和用户提示词

系统提示词放稳定规则：角色、输出格式、安全边界；用户提示词放本次任务：输入和特殊要求。把两者混在一起，改一次任务就要重写全部规则，很容易把之前调好的约束弄丢。我现在每个任务一个模板文件，版本号写进文件名里。
